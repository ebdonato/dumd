# AGENTS.md

## Build & Run

- **Dev:** `wails dev`
- **Production build:** `wails build -clean -ldflags "-s -w"`
- Do **not** use `go build` for production — Wails orchestrates the Go compile + Vite frontend build + embedding. Plain `go build` / `go install` work because `frontend/dist/` and the committed `internal/winres/*.syso` (Windows icon + manifest + version info) are in the tree (no `-H windowsgui`, no `-s -w`).
- First-time setup: run `npm install` inside `frontend/` before `wails dev`.
- Output binary lands in `build/bin/`.

## Architecture

- Go backend + vanilla JS frontend, glued by **Wails v2**.
- Go module name is `github.com/ebdonato/dumd` (required by remote `go install`).
- `main.go` — entry point, embeds `frontend/dist` via `go:embed`.
- `app.go` — all business logic (file I/O, Goldmark markdown→HTML, window control). Methods on `App` struct are auto-exposed to JS as Wails bindings.
- `console_windows.go` (`windows && !dev`) — per-monitor DPI and self-detach so console-subsystem `go install` builds release the terminal. Does not touch the window icon; that comes from the linked resource object (see below), which Wails' own window-creation code reads directly.
- `console_stub.go` (`!windows || dev`) — no-op stub.
- `resources_windows.go` (`windows && !dev && !desktop`) — blank-imports `internal/winres` to link the committed resource object into plain `go build`/`go install` binaries. Excluded from Wails builds (`dev`/`desktop` tags) because Wails compiles and links its own resource object; two would fail with "too many .rsrc sections".
- `frontend/src/main.js` — all frontend logic (keyboard handling, themes, zoom, IPC calls). Single file, no framework.
- `frontend/src/style.css` — all CSS including theme variables and typography.
- `frontend/wailsjs/` — **auto-generated** by Wails. Never edit.
- `frontend/dist/` — **auto-generated** by Vite build. Never edit. **Tracked in git** (needed by `go:embed` for `go install`). Rebuild with `npm run build` in `frontend/` and commit whenever `frontend/src/` changes. CI `dist-check.yml` fails if stale.
- No `vite.config.js` — Wails provides its own Vite defaults.
- Goldmark is configured with `extension.Table` (GFM tables).
- `internal/winres/` — **committed** Windows resource objects, `dumd_windows_amd64.syso` and `dumd_windows_arm64.syso` (icon, manifest, version info), so `go build`/`go install` binaries show the icon and file details on both Windows architectures. Generated by `tools/resgen` (`go run ./tools/resgen`), which mirrors Wails' resource compilation. Linked only via the blank import in `resources_windows.go` — never referenced directly. Deliberately *not* named like Wails' ephemeral `<name>-res.syso`: the GOARCH-suffixed filename keeps non-Windows toolchains from ever selecting it, and the `!dev && !desktop` build tag on the importing file keeps it out of every Wails build, so the Go linker never sees two resource objects at once ("too many .rsrc sections" otherwise). Regenerate and commit whenever `wails.json` info, `build/windows/icon.ico`, `build/windows/info.json`, or `build/windows/wails.exe.manifest` change. CI `dist-check.yml` fails if stale.
- `tools/resgen/` — standalone generator command; run with `go run ./tools/resgen [arch...]` (default: both `amd64` and `arm64`). Writes `internal/winres/dumd_windows_<arch>.syso` for each arch given.

## Key Behavior

- File path passed as CLI arg: `dumd readme.md`. Stored in `App.filePath`, read at runtime.
- If no arg is given, an empty-state welcome screen is shown.
- Themes: CSS classes `theme-dark`, `theme-sepia` on `<html>`. Default light has no class.
- Theme & zoom persist via `localStorage` (`dumd-theme`, `dumd-zoom`).
- `q` and `Esc` both quit the app (Esc closes settings popover first if open).
- Relative `.md` links spawn a new DuMD process (`OpenLocalMarkdown` uses `os/exec`).

## Testing

- `go test ./...` — `app_test.go` covers image-src rewriting and the local-file HTTP handler. No frontend tests; no test framework configured.

## Release

- No pre-commit hooks — `internal/winres/*.syso` is regenerated by hand with `go run ./tools/resgen` whenever `wails.json` info or `build/windows/{icon.ico,info.json,wails.exe.manifest}` change, same as `frontend/dist/`. CI (`dist-check.yml`) fails if it's stale, so a forgotten regeneration is caught, not silently released.
- Release workflow (`.github/workflows/release.yml`) triggers on `v*` tags; Linux/macOS jobs need no extra step — the GOARCH-suffixed filename in `internal/winres/` and the `!desktop`/`!dev` build tag on `resources_windows.go` already keep it out of non-Windows and Wails builds.

## Install (`go install`)

- Remote install: `go install -tags production github.com/ebdonato/dumd@latest` (Linux: add `webkit2_41`).
- Requires the module path to stay `github.com/ebdonato/dumd` and `frontend/dist/` + `internal/winres/*.syso` to be committed and current.
- `.github/workflows/dist-check.yml` enforces the dist/syso freshness (Ubuntu job) and, on a Windows job, that the `go build -tags production` binary actually carries the embedded resources (`ProductName` check) and that `wails build` still links cleanly (regression guard against a dual-`.rsrc` conflict).

## Constraints

- Binary must stay under **18 MB** (spec requirement).
- Idle RAM under **60 MB**.
- Frontend must remain vanilla JS — no framework bundles.
- Cross-platform targets: Windows x64, macOS (ARM + Intel), Linux x64.
